== 1. Tracking between students
=== I. What was expected
Requests should be tracked between different students. Meaning each student should have their own budget and the usage of one student should not affect the budget of another student.

=== II. Findings
At the current time LiteLLM does not have a built-in way to track usage between students. Also SSO was not setup for this evaluation. Meaning this point still has to be verified at a later time. +
However what could already be observed is that inside Swagger LiteLLM is able to differentiate between different users.

== 2. Setting a budget
=== I. What was expected
A Budget can be set and request spends were allowed to accumilate until the budget is exceeded.

=== II. Findings
LiteLLM clearly supports budgeting by: setting & tracking spend in USD,  allowing a budget reset period (daily, weekly, monthly) to be set and displaing what models were allowed.

==== Noteworthy:
Sometimes tiny budgets show up as 0$ however runtime enforcement errors show that the budget is 0.01$ for example.

== 3. Exceeding that budget
=== I. What was expected
Once spend exceeds the budget, LiteLLM should prevent any further model calls (no provider request, no additional cost).

=== II. Findings
Budget enforcement works and blocks calls immediately after the threshold is exceeded. +
LiteLLM recognizes acummulated spend and compares it to the Max budget, for example: 0.01$ -> 0.017$ => lead to a HTTP 400 Error & did not allow further calls. +

==== Evidence that calls are blocked before they hit the model provider
inside the logs of LiteLLM request that failed showed that no Tokens were used up and no costs were registered with the model provider. +
=> Exactly what was expected. LiteLLM blocks before any provider calls are made.

== 4. Further obersavations
Budget overshoot by last allowed request: +
In testing, a request was allowed while spend was still below the configured max budget, but its final cost pushed the total spend beyond the budget (e.g., total spend $0.0179 with max budget $0.01). This is consistent with budget enforcement that checks current spend before request execution and only blocks subsequent requests once the budget is exceeded. +
Risk: In large-scale deployments, these “final request overshoots” (and especially parallel request races) can accumulate over time. +
Mitigations: Set budget to 0.8$ / 0.9$ instead of 1$ to leave room for overshoot. Introduce a cap for request-tokens or implement a pre-call projected-cost check to avoid overshoot.
