== LibreChat vs Open WebUI: Feature Comparison for an AI Tutor Platform

=== Introduction

In this report, we compare LibreChat and Open WebUI – two open-source AI chat platforms – to determine which is better suited for an AI Tutor platform in schools. Both LibreChat and Open WebUI provide ChatGPT-style interfaces that can integrate with multiple large language models (LLMs), but they differ in feature sets, integration capabilities, and target use-cases. We will examine their functionalities, supported models, user interface intuitiveness, customization options, and other factors relevant to the project's requirements. The goal is to evaluate which platform can more effectively support the AI Tutors for Schools vision, or if neither fully meets the needs (implying that a custom solution might be necessary).

=== Project Requirements Summary

Before diving into the comparison, it's important to outline the key requirements of our AI Tutor platform (as described in the project vision and objectives):

* *Multiple LLM Support*: The platform must connect to various LLM providers (priority order: *Azure OpenAI*, *OpenAI*, *Anthropic Claude*, *Google Gemini*, *Mistral*, etc.). Teachers should be able to select the underlying model for each AI tutor instance.
* *Custom AI Tutors*: Teachers need to create AI tutor "profiles" by editing *system prompts* and configuring settings for each tutor. Students can interact with these tutors but cannot alter their configuration.
* *Multi-User Management*: The system should support multiple user roles (e.g. administrators, teachers, students) with secure authentication (ideally *Single Sign-On (SSO)* with school accounts) and the ability to manage users or groups (e.g. *class-based controls*).
* *Budget Control and Monitoring*: The platform must enforce *token or cost budgets* per user or class (per hour/day/week/month) and provide transparency – users and teachers should see their usage, and administrators can monitor *class-level* and *school-level usage* via dashboards.
* *Privacy and Self-Hosting*: All components (aside from the LLM APIs themselves) should be *open-source*, *self-hostable* on-premises or in *EU-based data centers*, and comply with *data protection* (no conversation data stored long-term, only minimal statistics). No user inputs should be sent to third-party services except the chosen LLM provider.
* *AI Tutor Capabilities*: Tutors should handle *text and image inputs* (e.g. a student uploading a photo of handwritten work), display mathematical formulas (*LaTeX*) and code correctly, and even perform computations or code execution (akin to a *"Code Interpreter"* for problem-solving).
* *User Interface*: The UI should be intuitive and familiar (chat-oriented), *accessible* (barrier-free for visually impaired users), and usable on common devices (primarily desktop/laptop web browsers, but also tablets and smartphones). A *responsive* or *mobile-friendly* design is needed, potentially with a *Progressive Web App (PWA)*.
* *Extensibility*: Integration with tools like web search or knowledge base (*Retrieval Augmented Generation (RAG)* for providing context/citations) is desirable. The system may need *plug-in support* (e.g. to incorporate coding tools or custom functions for the AI to use).
* *Deployment and Maintenance*: The solution must be *production-ready* (not just a prototype) and maintainable long-term. It should support *monitoring*, *logging*, and *scalability* (to handle many simultaneous users if needed). Minimal complexity in deployment is preferred due to limited IT resources in schools.

With these criteria in mind, we now compare LibreChat and Open WebUI across various dimensions.

=== Overview of LibreChat

LibreChat is an open-source chat interface inspired by ChatGPT's design, aiming to be a "fully customizable and compatible" client for many AI models. It is released under the MIT License. LibreChat's development is noted for its rapid integration of new models and providers – whenever a major LLM is released, LibreChat typically adds support within the same week. Originally pitched as an "enhanced ChatGPT clone", LibreChat extends the familiar chat experience with numerous additional features and settings.

Key features of LibreChat include: *multi-provider model selection*, *conversation history search*, *conversation branching* (edit and resend messages), *custom presets* for configurations, and a *plugin system* built on *LangChain* for tools and external data access. It also offers *multi-user identity management* with secure logins (including *OAuth2/OIDC* for Google, Microsoft, etc.), enabling an *enterprise-level authentication* setup. LibreChat emphasizes *privacy*, allowing *self-hosting* and control over *data retention* (such as "incognito" temporary chats that won't be saved). Overall, LibreChat targets use-cases where *flexibility* and *integration* with various AI services are needed in one unified interface.

=== Overview of Open WebUI

Open WebUI is an extensible, self-hosted AI chat platform (Apache 2.0 License) designed to run entirely offline or with custom API connections. It supports multiple back-ends, including local model runners like Ollama and any OpenAI-compatible APIs, effectively letting users mix local and cloud models in one interface. Open WebUI is positioned as a user-friendly solution with a focus on easy setup (Docker/Python installers) and robust features for deployment, scaling, and enterprise integration.

Notable features of Open WebUI include: granular *Role-Based Access Control (RBAC)* with *user groups* and *permissions*, a *responsive design* with full *mobile support* and even a *Progressive Web App (PWA)* mode for offline use, and rich support for *Markdown/LaTeX* in chat for formula rendering. It incorporates *voice and video chat* capabilities using multiple *Speech-to-Text (STT)* and *Text-to-Speech (TTS)* engines, which is useful for *accessibility* and hands-free usage. Open WebUI also has a built-in *"Model Builder"* to create or import local models (e.g. fine-tuning via *Ollama*) and create *custom chat agents/characters* via the UI. Furthermore, it provides advanced tools like *Python function calling* (allowing integration of custom Python functions that the AI can execute), and strong *Retrieval-Augmented Generation (RAG)* support with a choice of *vector databases* and *web search providers*. Open WebUI is actively maintained with frequent updates, and even offers enterprise-oriented options (e.g. *SCIM provisioning*, *SSO* with *LDAP/AD*) for organizational use.

=== Detailed Comparison and Analysis

==== Supported Models and Integrations

*LibreChat:* One of LibreChat's strongest advantages is its support for a wide array of *AI model providers* out-of-the-box. It natively integrates with *OpenAI* (*ChatGPT API*), *Azure OpenAI Service*, *Anthropic's Claude*, *Google PaLM2*, and even *Bing AI*, among others. This means the platform can serve as a *unified front-end* to many third-party AI services. Whenever a new model API becomes available, LibreChat's maintainers tend to add it quickly. Furthermore, LibreChat allows configuration of *custom endpoints*: for example, hooking up to a local *Ollama* server or *Hugging Face Inference API* is possible by editing the `librechat.yaml` config file. In short, LibreChat is oriented towards using *externally hosted models* (cloud or self-hosted via API) rather than running models internally. This approach aligns with our project's need to connect to *Azure OpenAI* and others with minimal hassle. It also means running LibreChat itself does not require *heavy compute resources* – the heavy lifting is done by the model providers.

*Open WebUI:* Open WebUI also supports connecting to *external model APIs*, but its design places equal (if not greater) emphasis on *running models locally*. It comes with integration for *Ollama*, which is a system for serving local *LLaMA-family models* efficiently. In practice, Open WebUI can be pointed at any *OpenAI-compatible REST API*; by configuring the API base URL, you can use services like *OpenAI*, *Azure*, *OpenRouter*, etc., similarly to LibreChat. It additionally mentions compatibility with *LMStudio*, *GroqCloud*, *Mistral* and other services that present an OpenAI-like interface. A unique feature of Open WebUI is its ability to use *multiple models concurrently* – it supports chats where different turns are answered by different models, or even *merging outputs*, which can be useful for comparing model behavior or *ensemble responses*.

In summary, both platforms meet the requirement of multi-LLM support. LibreChat might have a broader set of ready-to-use integrations (since it specifically lists Anthropic, Google, etc., and even non-API models like Bing via reverse engineering). Open WebUI's support is broad too, but it assumes either the use of an OpenAI-compatible API or running your own instances. If our use-case involves primarily Azure OpenAI and possibly OpenAI/Anthropic, both platforms can accommodate those easily. If we consider future use of fully open models (like Mistral or LLaMA 2) for cost-saving, Open WebUI has an edge because it can host them internally (with a GPU server), whereas LibreChat would require an external serving solution (which we then integrate via an API).

==== User Interface and User Experience

Both LibreChat and Open WebUI provide a modern chat interface reminiscent of ChatGPT, but there are some differences in user experience details:

* *LibreChat UI:* It strives to make users comfortable by mirroring the ChatGPT layout – a sidebar of conversation threads, a main chat panel, and input box. Users can start new chats, and importantly fork conversations or edit messages to branch off alternate replies. This is very useful in an educational context: a teacher or student can modify a question slightly and see a different answer without starting from scratch. LibreChat also includes a conversation search bar, which is great for quickly finding past discussions (e.g., a student searching what the tutor said about a certain topic earlier). The interface supports displaying images and files in the chat, since it has an "Upload as Text" and OCR feature for images – for example, a student could upload a photo of homework and the system could extract text. Overall, LibreChat's UI is reported to be intuitive, though deploying it may require some configuration. It does not explicitly mention mobile optimizations; presumably it works on a tablet/phone browser but some UI elements (like wide tables or code blocks) might be less convenient on small screens.
* *Open WebUI UI:* Open WebUI takes a very feature-rich approach to the interface. It includes quality-of-life features such as syntax highlighting and a floating "copy code" button on code blocks for easy copying, interactive elements like being able to edit code within the chat result and re-run it (if using the code execution tool), and even special actions when selecting text (like a quick "explain this" prompt). These can greatly enhance user engagement, especially for programming classes (students can test code outputs right away) or language classes (quickly ask for explanation of a phrase). The UI is responsive: it has a collapsible sidebar that can be swiped in/out on mobile, and it supports installation as a PWA (so users can launch it like a mobile app and even get offline access for local models). This focus on responsiveness indicates Open WebUI might provide a smoother experience on iPads or smartphones out-of-the-box. It also supports both rich text input (with formatting) and a plain text mode, catering to user preference. For multilingual needs, Open WebUI can switch the chat direction (RTL vs LTR) for languages like Arabic or Hebrew, and the UI text itself can be translated (it has i18n support, and community translations).

In an educational setting, both UIs should be easy for students to use since they mimic familiar chat interfaces. LibreChat's closer resemblance to ChatGPT could mean less initial learning curve for new users. Open WebUI's additional UI features provide more power but could potentially overwhelm very novice users with options. However, many of those features (like editing or multi-model chat) are optional and can be ignored unless needed, so the interface can still be used simply. Importantly, both support Math and Code rendering – so a tutor's output with formulas or programming snippets will appear properly formatted. This fulfills the requirement that AI tutors can display math and code correctly.

==== Customization and AI Tutor Configuration

Our project requires that teachers be able to customize AI tutors (system prompts and behaviors) and possibly have multiple such tutors configured. Let's see how each platform supports that:

* *LibreChat – Custom Agents and Presets*: LibreChat offers a concept of *"Agents"* or *custom assistants* which can be created with *no-code* through the UI. A teacher could define a new agent, set a name/persona (e.g. "Algebra Tutor"), and provide a *system prompt* or example dialogues to steer its style. Because LibreChat supports multiple models, the teacher can also choose which model (*OpenAI GPT-4*, or *Claude*, etc.) that agent will use. Additionally, LibreChat's *preset feature* allows saving specific combinations of *model parameters* and prompts as *one-click presets*. This means a teacher could configure a tutor (prompt + model + temperature etc.), save it, and easily reload it for a class. *Conversation branching* also means a teacher can demonstrate alternative tutor responses by adjusting prompts and not lose the original conversation. One caveat: out-of-the-box, LibreChat might not have a polished interface specifically for "managing multiple tutors for a class" – it has the building blocks (*agents* with *shareable links* perhaps, since it supports shareable conversation links), but ensuring students only access the tutors intended for them might require some administrative setup (possibly separate accounts or providing them preset links).
* *Open WebUI – Custom Characters and Pipelines*: Open WebUI similarly allows creating *custom AI characters/assistants* in its interface. One can set a *persona* and even an *avatar image* for the assistant. It supports *importing and exporting* these configurations so they can be shared or replicated across instances. For deeper customization, Open WebUI's *Pipeline plugin system* can be used to tailor how the AI responds. For instance, one could implement a pipeline that filters or transforms user inputs (to enforce certain *pedagogical rules*) before they reach the model, or *post-process model outputs* to ensure they align with school policies (e.g. remove profanity, etc.). This level of customization is very powerful but requires *programming skill*. On the simpler side, a teacher could just operate multiple chats each with a different model and initial prompt to mimic different tutors. Open WebUI's *channel feature* (*real-time chat rooms*) might even allow a scenario where a teacher and a group of students share a chat with a tutor bot present – useful for *group discussions* or demonstrations.

Both platforms allow mid-conversation model switching and prompt editing (LibreChat explicitly allows switching AI endpoints mid-chat without disruption, and Open WebUI can do the @modelname switching or merging responses). This flexibility is great for experimentation, but in a controlled classroom scenario we might lock a given tutor to one model.

In terms of UI customization, LibreChat can be configured with custom UI elements via its YAML (for example, one can simplify the interface by hiding certain model choices from users). Open WebUI offers theming (with the enterprise version offering easier branding) and layout settings as well. Since accessibility is key, we should note that both allow enabling speech features (which could be turned on or off per assistant).

Summary: For creating distinct AI tutors (like one per subject), both platforms provide mechanisms. LibreChat's approach might be slightly more straightforward for a non-developer (define agent in UI with prompt and pick a model) and save it. Open WebUI can achieve the same, but also gives an option to deeply customize behavior through plugins if needed.

==== Multi-User Management and Security

In a school environment with potentially hundreds of student users and dozens of teachers, the platform must handle authentication, user accounts, and permissions reliably.

*LibreChat:* *Multi-user support* in LibreChat is built-in; it has a registration and login system with *email/JWT* and can integrate with external *OAuth providers* (*Google*, *Microsoft Entra ID*, etc.). This means we can likely plug it into the school's *Azure AD (Entra ID)* via *OIDC configuration* for *SSO*, meeting the extended goal of SSO integration. When it comes to roles, by default it may have just *"admin"* and *"user"* roles. Admins can manage *system-wide settings* and perhaps view all conversations or *usage stats*, while normal users can only see their own. The Cloudron forum notes that LibreChat is considered an *"enterprise-level"* solution in terms of *authentication flexibility*, but it might lack some *granular admin controls* that Open WebUI has. For instance, it's not clear if LibreChat natively supports *grouping users into classes* or *restricting certain models* to certain users (that might require manual configuration). It does, however, log *usage per user* – the mention of *token spend tools* suggests an admin could see how many tokens each user consumed and perhaps set *quotas* (there is a *Balance* configuration in the docs, implying *per-user credit* could be assigned). Enforcing a strict *budget window* (e.g. monthly limit) might require a *custom script* unless that feature exists in LibreChat's latest version (not explicitly documented in the sources we found).

*Open WebUI:* This platform shines in *enterprise user management*. It supports full *RBAC*, meaning we can create *roles* like *"Teacher"*, *"Student"*, *"Admin"* and assign *capabilities* accordingly. For example, we could allow only teachers and admins to create new AI agents or use certain powerful models, while students can only chat with *pre-approved tutors*. Open WebUI also integrates with *LDAP/AD* and *OAuth providers* natively, which covers our *SSO* requirement (*Azure AD* can be used either via *OAuth2 OIDC* or *SAML* as listed in documentation). Another critical enterprise feature is *SCIM 2.0* support for *user provisioning*, meaning if the school's directory updates (new student, etc.), it can *automatically update* the user list in Open WebUI. This level of integration is beneficial for *maintenance* in a *large deployment*.

Open WebUI also hints at user grouping – since it has channels and user status indicators, one can imagine mapping a class to a channel or group. It's not exactly the same as class-level enable/disable of a tutor, but one could potentially create separate workspaces for each class. At minimum, an admin UI exists for managing users and their permissions.

Regarding usage monitoring: Open WebUI itself does not explicitly mention a UI for token usage per user, but it does have the capability to log all interactions and through its pipeline plugins one could implement user-specific rate limiting or usage tracking. For example, a plugin could intercept each API call and decrement a counter per user, disabling further calls if a budget is exceeded. This would require some development, but the framework supports it. In contrast, LibreChat might already include a simple budget system (perhaps each user could have a token balance configured that the app deducts from on each query – indicated by the "Balance" config).

Security and Privacy: Both being self-hostable, we have control over data. LibreChat emphasizes privacy – conversations can be ephemeral (Temporary Chat mode) and presumably it does not store user queries beyond what's needed for conversation history (which can be turned off or wiped). Open WebUI, by virtue of being offline-capable, also ensures data stays on your servers. Both have moderation or filtering features: LibreChat lists Automated Moderation in its docs (likely to filter toxic content), and Open WebUI's pipelines mention a Toxic Message Filtering example. These are important for a school setting to prevent misuse.

In conclusion, for multi-user, multi-role management, Open WebUI offers a more comprehensive solution out-of-the-box. If class-based toggling of features is crucial, Open WebUI's RBAC can approximate that by configuring roles for each class or group. LibreChat can still be used in multi-user mode but might require more manual oversight to ensure students only do what they are permitted to do. Both can be integrated with school SSO, though Open WebUI has a slight edge in enterprise readiness (with SCIM, etc.).

==== AI Capabilities: RAG, Code Execution, and Plugins

A key differentiator for our AI Tutor platform is the ability for the AI to assist with tasks like solving math problems (possibly by running code or calculations) and providing references or working with uploaded class materials. Both platforms extend beyond basic chat in these areas:

* *Retrieval-Augmented Generation (RAG)*:
** LibreChat supports RAG via a *"Chat with Files"* feature using a *RAG API*. A teacher or student can upload documents (PDFs, text, etc.) and ask questions about them. Internally this likely uses an *embedding-based search* (perhaps with a simple *vector store*). However, it's noted that LibreChat's *file management* is not very advanced – it may handle a handful of files for Q&A, but it might not scale to a *large library* or allow rich organization of *knowledge bases*.
** On the other hand, Open WebUI has an *elaborate RAG system*: it supports *9 different vector databases* (*ChromaDB*, *Pinecone*, etc.) and multiple *document parsing engines*. It allows adding files to a *persistent library* and even using a special syntax (#filename) to pull in documents on the fly during a chat. It also can perform *web searches* using various providers to fetch information on demand. Additionally, Open WebUI's RAG feature automatically adds *citations* to the chat responses, showing the source of information – a useful feature in education to teach students about referencing sources. It even has advanced options like *hybrid search* (combining keyword and vector search) and *YouTube transcription summarization pipelines*. The downside mentioned in community notes is that Open WebUI's RAG might become complex or less efficient with *very large document sets* (perhaps requiring more memory or fine-tuning), but for a classroom with a moderate set of materials, it should suffice.

* *Code Execution / "Code Interpreter"*:
This is extremely valuable for subjects like *mathematics* or *programming*, and both platforms address it. LibreChat includes a *Code Interpreter API* which allows the user to request code to be run in various languages (*Python*, *JavaScript/Node*, *C/C++*, etc.) and return the result. This is analogous to OpenAI's Code Interpreter plugin – for instance, a student can ask the AI tutor to plot a graph or solve a calculation, and the AI can execute a Python snippet and return an image or answer. LibreChat's documentation emphasizes *secure*, *sandboxed execution* across multiple languages, which is crucial for security (no arbitrary server access). Open WebUI approaches this via its *Native Python Function Calling Tool*. Essentially, an administrator can register certain *Python functions* or allow *limited code execution* that the LLM can trigger. Open WebUI's UI has a *"tools workspace"* with a *code editor*, so presumably the AI's generated code can be executed and the results are fed back into the chat. This is powerful but might require more setup (defining which functions are allowed, etc.). For our use, both solutions could enable a *"sandbox math solver"* in the AI tutors. LibreChat might have a slightly simpler user experience (just ask in plain language and it decides to run code if needed), whereas Open WebUI might present it as a more explicit tool. In either case, achieving the "AI that can calculate or run code" goal is possible.

* *Plugins and Tools*:
Beyond code and RAG, LibreChat's *LangChain plugin system* means it can integrate all sorts of tools – from *web search* to *WolframAlpha*, or custom ones. In fact, the LibreChat docs mention plugins for search and even *Stable Diffusion* or *Wolfram|Alpha*. Because it leverages *LangChain*, one could script an *agent* that uses multiple tools in sequence. Open WebUI's *pipeline* is analogous, but perhaps more *developer-centric* (write Python to extend functionality). It lists examples like *live translation* (using *LibreTranslate*), and *usage monitoring* as possible pipeline plugins. One notable tool integration for Open WebUI is *web browsing with context injection*: by using #<url> in the chat, the content of that URL can be pulled into the conversation. This could allow an AI tutor to, say, retrieve a Wikipedia article snippet if needed – though caution is needed in exams!

Overall, both platforms excel in extensibility. They ensure that we can equip our AI tutors with extra capabilities needed for education (be it solving equations, drawing diagrams, or referencing class notes). Open WebUI has the edge in RAG and knowledge integration, which might be significant if we plan to load it with textbooks or class materials so the tutor can cite them. LibreChat's advantage is that it is piggybacking on the rapidly evolving LangChain ecosystem, which could make adding new tools relatively straightforward.

==== Deployment, Scalability, and Maintenance

The final aspect to consider is the practicality of deploying and maintaining either platform in a school's IT environment.

LibreChat Deployment: LibreChat offers multiple deployment methods: a *Docker Compose* setup, an *npm (Node.js)* based setup, and even *Helm charts* for *Kubernetes*. Users have noted that its Docker setup, while robust, can be a bit complex or "over-engineered" with multiple containers (database, etc.). In our case, since we require *on-premises hosting*, *Docker* is likely a good route. The school's IT team would need to host a *MongoDB* (or use *MongoDB Atlas* if allowed) and the LibreChat server. The *memory/CPU requirements* for LibreChat itself are not high (since it's mostly a web app delegating to APIs), which is a plus. One instance could potentially serve many users, though we might scale it by running *multiple instances* behind a *proxy* if needed. Configuration of all the desired providers (Azure OpenAI, OpenAI, etc.) must be done via *config files* or *admin interface*, which takes initial effort but is one-time. LibreChat keeps conversation data in a database (unless using *temporary mode*), but we can configure *retention policies* or ask it not to store content to meet privacy concerns. *Automatic updates* would require manually pulling new versions; given the active development, we'd want to periodically update to get new features or bug fixes.

Open WebUI Deployment: Open WebUI is similarly *containerized*. There is an official *Docker image* that can run with *CPU* or *GPU*. If we include the *Ollama* (local model) component, the image is large (since it might bundle a model or at least the runtime). The forum discussion suggests Open WebUI's image is "massive" and requires caution on first download. In practice, if we plan to rely mostly on Azure/OpenAI models, we could run the Open WebUI container in a mode that doesn't preload local models (for example, using the `:api` tag or setting `OPENAI_API_KEY` so it focuses on external API). Open WebUI stores its state in a *SQLite* database by default (mounted on a volume) or can use *PostgreSQL* for *multi-instance setups*. It also uses *Redis* when scaling out to multiple nodes for *session management* – this indicates the developers have considered *multi-instance scaling* which is beneficial for reliability. Monitoring hooks via *OpenTelemetry* mean it can integrate with dashboards if the school has any (or we can deploy something like *Grafana/Prometheus* to watch it).

From a maintenance perspective, Open WebUI's enterprise features like *SCIM* for *user provisioning* might simplify user management as classes change – it can *automatically sync* with the directory. With LibreChat, adding/removing users might be a bit more manual unless one writes a script or uses its API if available. Both communities are active; however, it appears Open WebUI has a *commercial backing* (offering an *enterprise plan* and careers page), which might mean more *rapid professional development* and support. LibreChat is *community-driven* and has an enthusiastic open-source community as well.

Performance: If many students simultaneously use the AI tutors, the bottleneck will likely be the *LLM API usage* rather than the UI. Both UIs can *queue* or handle *multiple conversations asynchronously*. Open WebUI explicitly supports *asynchronous chat* – you can start a query, leave the chat, and come back to see the answer when it's done. This *non-blocking behavior* is great for handling heavy queries (e.g., code execution or large searches) without freezing the UI. LibreChat likely handles multiple sessions with separate threads/processes communicating to the AI APIs (especially since it supports conversation branching, which implies it can manage *multiple parallel prompts*).

In terms of fit for a permanent school operation, both solutions will require initial setup and some customization (especially around user management and usage control). Open WebUI might require a bit more server muscle (particularly if we venture into local models or heavy concurrent usage, where vertical scaling or GPUs help). LibreChat is lighter, but if we only use external APIs, the cost will be in API usage (hence the need for budgeting).

==== Accessibility Considerations

A crucial requirement is that the platform be barrier-free, including usability for blind or visually impaired users. Both being web-based means they rely on the accessibility of modern web applications. This typically includes support for screen readers (through proper HTML semantics) and keyboard navigation. Neither project's documentation explicitly details compliance with standards like WCAG, so we should evaluate their features:

* *LibreChat*: With a straightforward design (text boxes and buttons), it should work reasonably with *screen readers*, though there might be minor issues (for example, dynamic content like new chat messages might need *ARIA live regions* – unknown if implemented). The *Hands-Free Chat* feature is a strong point: users can use *speech-to-text* to ask questions and *text-to-speech* to hear responses. For a blind student, this could allow *near-complete hands-free operation* with the AI. We would need to test it to ensure that *keyboard focus* is managed (so that pressing tab or using screen reader shortcuts can reach all elements like the message input, history list, etc.). If needed, since it's open source, we could enhance the UI for accessibility (adding missing labels or adjusting *color contrast*) as part of our implementation.
* *Open WebUI*: This platform's inclusion of *voice input/output* is also a major benefit for accessibility. Additionally, features like *haptic feedback* are indirectly helpful (confirmation of actions via vibration can assist some users). The *responsive design* means on different devices, it adapts the layout, which often is good for accessibility (e.g., one-column view on mobile can be easier to magnify). Open WebUI's *multi-modal support* could allow, for instance, a student to upload an image and have the AI describe it (if an appropriate model is used), which is an accessibility tool in itself (*image-to-text* for blind users). We should verify if Open WebUI's chat interface properly labels buttons and sections for screen readers. Given its active development, there's a good chance improvements can be contributed if not already present.

Conclusion on accessibility: Both platforms offer *voice interactions* and are web-based (leveraging browsers' accessibility features), so they can be made to meet our requirement. Open WebUI's thoroughness in features doesn't exclude accessibility, but we must ensure that introducing many features doesn't clutter the experience for disabled users. It might be prudent to conduct *user testing* with these groups if possible, but from a feature standpoint, both LibreChat and Open WebUI are capable of being used in an accessible way, with Open WebUI having a slight edge in *out-of-the-box mobile/voice integration*.

==== Suitability for the AI Tutor Project Goals

Now we evaluate how well each platform addresses the specific goals of the AI Tutors for Schools project:

* *Integrating Multiple AI Models*: Both LibreChat and Open WebUI satisfy the need to connect to *Azure OpenAI*, *OpenAI*, and other providers. LibreChat has *explicit support* and a *quick integration cycle* for providers like Azure, Anthropic, etc., making it very convenient. Open WebUI also supports these via *API keys* and even allows *hosting open models* (e.g., for *Mistral* or *LLaMA*) internally. If our priority is using Azure/OpenAI initially, either is fine. If we anticipate leveraging *open-source models* (to reduce token costs or ensure data never leaves premises), Open WebUI is more prepared to do so directly, whereas LibreChat would need an external service (which could be an additional component to maintain).
* *Custom AI Tutors (Prompts & Configurations)*: LibreChat provides *no-code creation* of custom assistants and saving presets, which aligns well with letting teachers configure tutors with particular prompts and settings. Open WebUI also allows *custom "characters"* with specific initial prompts and settings. Both can support having *multiple named tutors* that teachers set up and students use. The difference might come in how these are presented: LibreChat might treat each as just a conversation with a certain preset; Open WebUI might allow a more *persistent character profile*. Either way, we have a means to create and manage several distinct tutor personas. Neither platform inherently restricts students from changing the prompt or model if they have access to the UI controls (for example, a savvy student could switch the model mid-chat unless the UI is locked down). Here, Open WebUI's *RBAC* could be useful: we could create a role for students that does not permit changing the model or certain settings, whereas teachers/admin role can. In LibreChat, we might have to rely on trust or *custom UI modifications* to hide those controls from student users.
* *Budget Control*: This is a complex requirement not fully met by either platform out-of-the-box, but both provide partial solutions. LibreChat tracks *token usage per user* and likely could support setting a *token limit* (the presence of *Transactions* and *Balance* in config suggests functionality to allocate credits). We would need to verify the latest LibreChat docs or code to see if it has an *admin panel for budgets*. If not, implementing a simple check (like deducting from a stored balance on each API call) might be possible since the system is already aware of token usage. Open WebUI doesn't explicitly enforce budgets internally, but using its *plugin framework*, one could implement *"user rate limiting"* as mentioned. Also, because Open WebUI can integrate with external monitoring (*OpenTelemetry*), we could track usage in a monitoring tool and even *automatically deactivate accounts* that exceed quota by calling an admin API. In either case, some *custom development* or scripting will be needed to robustly enforce budget limits and reset them periodically. This is an area where a *custom solution or add-on* might need to be built on top of whichever platform we choose.
* *Ensuring Educational Features*: Displaying math and code is handled well by both (full *Markdown + LaTeX* support). The *code execution feature* (*Code Interpreter*) is present in both, which is a huge plus for us. Both allow *image input*. LibreChat explicitly mentions accepting *image uploads* and running *OCR*, which could cover "photo of handwritten work" scenario by extracting text for the AI. Open WebUI can accept images and if using a *multimodal model*, interpret them directly, or potentially one could integrate an *OCR pipeline* as well. Additionally, both support some form of plugins for specialized tasks (like a *calculator* or *WolframAlpha* for precise math), which can be leveraged to strengthen the AI tutor's reliability in subjects like math.
* *Administrative Dashboard*: The requirement that school leadership can view *total usage by class* could be approached via Open WebUI's *user grouping* or *SCIM* (if classes are groups in AD, we could mirror that and tally usage per group). Neither platform ships with a pre-built *"usage dashboard"*, so that is likely something we'd implement via *log data* or *database queries*. For example, LibreChat could store token usage in *MongoDB* and we could create a small page or script to aggregate by class (if class information is embedded in user profiles). Open WebUI might allow writing a plugin or using the *telemetry data* for similar analytics. This is a non-trivial extension but feasible since data is available; it's more about presentation.
* *Privacy & Compliance*: Both being *self-hostable* and not sending data anywhere except to the chosen model API is compliant with the schools' requirements. LibreChat explicitly states a focus on *privacy* and *control over data*. Open WebUI being *offline-capable* is inherently *privacy-preserving* (if using local models, no data leaves; if using APIs, it's up to us to choose trusted endpoints like Azure in EU regions). We will have to configure both to disable any *telemetry* or *community-sharing features* (Open WebUI has a "share to community" function that we'd turn off in a school setting). With careful configuration, both platforms can be used in a *GDPR-compliant* way (e.g., not logging personal data unnecessarily, allowing deletion of user data on request, etc.).
* *Maintainability and Transferability*: The project needs to be *reusable by other schools*. On this front, using an *open-source solution* is advantageous as others can adopt it without licensing issues. LibreChat being *MIT* and Open WebUI *Apache 2.0* means no problematic restrictions. *Packaging* either solution with our custom configurations for other schools is possible. LibreChat might be slightly simpler for another school to adopt if they just want an easy ChatGPT alternative – they could spin it up and plug in their keys. Open WebUI might appeal to more *technically inclined schools* or those wanting to host models. Documentation-wise, Open WebUI has *extensive docs* (and presumably support channels), while LibreChat also has docs and a community. We might consider the *learning curve*: which would a typical school IT admin find easier? There are hints that Open WebUI is easier to set up for basic use (it's described as *"user-friendly"* and an easy setup especially if using just API keys), whereas LibreChat might require more configuration to fully utilize (but *Cloudron packaging* or similar can simplify it). In a forum comparison, it was suggested that LibreChat is *"more difficult to deploy"* than Open WebUI, but adding it to a managed platform would give more value due to that complexity. This implies that if we handle the deployment expertise, either is fine, but for wide adoption among many schools, a *smoother installation process* is a plus.

Considering all these factors, we can say both LibreChat and Open WebUI are strong contenders for the AI Tutor platform foundation. Each covers the core requirements but also has some gaps that might need custom development (particularly around fine-grained user controls and usage budgeting). The final decision may come down to which aligns better with our priorities:

* If we prioritize *simplicity*, a *smaller system footprint*, and *leveraging cloud AI services* extensively, LibreChat could be preferable. It would let us plug in our *Azure OpenAI keys* and get started quickly with a familiar interface, and we would extend it as needed for budgets or class management. It's described as *mature* and *effective* for using various model APIs without needing *specialized hardware*.
* If we prioritize *extensibility*, *enterprise integration*, and the option to use *on-premise models* for cost or data reasons, Open WebUI might be the better fit. It offers a more *comprehensive feature set* aligned with enterprise scenarios (*RBAC*, *SCIM*, *horizontal scaling*) which indicates it can grow with our needs. It is also *actively evolving* with new features that could prove useful (like *multi-agent channels*, *advanced RAG pipelines*, etc.). The trade-off is *higher complexity* and possibly unused features.

Lastly, it's worth acknowledging that neither platform will cover 100% of our ambitious goals without some customization. For example, neither has a built-in notion of "class periods" or an interface for teachers to toggle tutor availability by class – that would likely need to be custom-built on top of the chosen platform. Similarly, enforcing budget limits per time period may require patching in our own logic. The decision should factor in which platform's architecture and community would make those extensions easier.

=== Conclusion and Recommendation

LibreChat and Open WebUI are both powerful open-source chat platforms, each with a rich set of features that map well to the needs of a school AI Tutor system. LibreChat offers a slightly more straightforward approach focused on using external AI services with a familiar ChatGPT-style user experience, making it quick to get started with multiple models and straightforward for users (teachers and students) to adopt. Open WebUI provides an enterprise-grade solution with greater extensibility and the flexibility to run models locally, which can future-proof the platform for offline use or reduce dependency on cloud APIs.

Our evaluation finds that both could be used as a foundation, but they excel in different aspects: LibreChat in *ease of integration* and *multi-model switching*, and Open WebUI in *administrative control* and *advanced tool integration*. If we consider immediate deployment for a pilot at HTL Leonding, LibreChat might be the slightly better choice for *initial simplicity*, especially if the school's infrastructure is limited (no GPUs) and we plan to rely on Azure/OpenAI anyway. It will "work with all existing hardware" and let us pay only for *API usage*. On the other hand, Open WebUI offers more *long-term scalability* and *customization*; for a *production system* that could be adopted by many schools, its *robust user management* and ability to incorporate new technologies (like different model backends, or deep integration with school data) is a significant advantage.

Recommendation: We recommend taking a closer look at *Open WebUI* as the platform for the *full-scale implementation*, given its alignment with *enterprise* and *education sector requirements* (*SSO*, *RBAC*, *scalability*, *offline capability*). It appears to be designed with *organizational deployment* in mind, which suits a *permanent school installation*. However, adopting Open WebUI might require disabling or tailoring some of its features for simplicity (to avoid overwhelming users) and writing some *custom plugins* for things like *budget enforcement*. LibreChat remains an excellent option if our priority is to get something running quickly that closely mimics the *ChatGPT experience* with *minimal configuration* – it could even be used as a *stop-gap* or a *parallel trial*.

If, during prototyping, we find that neither LibreChat nor Open WebUI can meet critical requirements (for instance, if budget control or specific accessibility needs cannot be reasonably added), we may conclude that a custom-built solution is necessary. Building from scratch would allow us to implement exactly the features needed for educational settings, but it's a much larger undertaking and would duplicate a lot of functionality that these platforms already provide. Given the time and resource constraints, leveraging one of these open-source platforms and extending it appears to be the most efficient path. We should only resort to a fully custom platform if absolutely required.

In summary, both platforms are viable, but *Open WebUI* slightly edges out for a *long-term*, *robust AI tutor service* due to its *comprehensive features* and *scalability*, whereas *LibreChat* wins on *immediate ease-of-use* and *lightweight deployment*. The ultimate choice should consider which trade-offs we are more willing to manage. Regardless of choice, expect to invest in some *custom development* to tailor the platform to our *school-specific needs*.
